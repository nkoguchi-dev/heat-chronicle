# Heat Chronicle プロダクト仕様書

このディレクトリは、Heat Chronicleについて、利用者から見える決定事項を管理する。

## 仕様書の責務

Markdown仕様書は、次の事項の正本とする。

- プロダクトや画面の目的、想定利用者、提供価値
- 提供する機能と対象外の機能
- 表示内容、利用者の操作、画面状態、エラー時の振る舞い
- 利用者に影響する制約とアクセシビリティ要件

APIのフィールド、HTTPステータス、関数、型、コンポーネント、状態管理、テストの実装方法など、利用者向け仕様を変えずに変更できる内部構造は記載しない。

## 文書の構成

| 文書                                         | 役割                                                 |
| -------------------------------------------- | ---------------------------------------------------- |
| [`product.md`](./product.md)                 | プロダクトの目的、利用方法、提供範囲、全体要件と制約 |
| [`ui/heatmap.md`](./ui/heatmap.md)           | ヒートマップ画面の表示、操作、状態、URL復元          |
| [`ui/heatmap.feature`](./ui/heatmap.feature) | ヒートマップ画面の受け入れ条件                       |

## Markdown仕様書とGherkin

Markdown仕様書を利用者向け仕様の正本とし、Gherkinはその受け入れ条件を、利用者の操作と観測可能な結果で具体化する。両者が矛盾する場合はMarkdown仕様書を優先してGherkinを修正する。

GherkinにはAPI呼び出し、レスポンス値、内部状態、関数、コンポーネント名を記載しない。クエリパラメータのキー名や変換規則などの実装契約は、Unit、Integration、Componentテストで確認する。

各ScenarioとScenario Outlineには、次のいずれかを付ける。

| タグ          | 対象                                                                         |
| ------------- | ---------------------------------------------------------------------------- |
| `@smoke`      | 直接アクセス、地点選択、気温種別切替、過去データ追加、履歴復元などの主要導線 |
| `@regression` | 境界、エラー、再試行、ローディング、アクセシビリティなどを補完する振る舞い   |

タグはテスト層を直接指定しない。最適なテスト層は[テスト戦略](../TESTING_STRATEGY.md)に従って選び、Gherkin全件をBrowser Smokeへ重複実装しない。

## 仕様変更

利用者から見える振る舞い、提供範囲、制約、受け入れ条件を変更する場合は、実装と同じPull RequestでMarkdown仕様書と関連するGherkinを更新する。技術上の事実だけが変わる場合は利用者向け仕様への影響を確認し、影響がなければ仕様書を変更しない。

仕様書にない利用者向け判断が必要になった場合は、実装前にIssueへ判断内容を反映する。仕様関連文書を変更したPull Requestでは、[仕様書レビューガイド](../REVIEW_GUIDE_SPECS.md)に沿って自己レビューする。
