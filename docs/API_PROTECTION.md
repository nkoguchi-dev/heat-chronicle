## 現在の実装と未確認範囲

- `get_temperature`は地点を照合し、終了年から最大50年分を読む。終了年の上下限はなく、READMEにある`start_year`引数は現行ルートには存在しない。
- `fetch_month`は地点と月1〜12を検査し、未来月は空配列を返す。観測開始前の年月を拒否する境界はない。
- 鮮度判定は確定済み月を再取得せず、未確定月は24時間キャッシュする。月末から2日を過ぎて取得した月を確定済みとする。
- ブラウザは月単位で直列取得し、応答後2秒待つ。これは直接APIを呼ぶクライアントへの制限にならない。
- 気象庁クライアントは30秒timeout、最大3回の試行。取得前の共有ロック・全実行環境共通の間隔制御はない。同じ未取得月への並行リクエストは重複取得しうる。
- TerraformはHTTP APIの`$default`ルートから単一Lambdaへ転送する。stageの流量設定、Lambda reserved concurrencyは未定義。Lambda timeoutは900秒。
- 以上はコードの事実。本番設定との一致、実測レイテンシ、通常同時利用数は未確認。AWS SSO認証復旧後の照合は#196・#199で別途行う。

## 入力契約（#198）

暦の判定は日本時間で統一し、1リクエスト開始時の日時を固定する。地点の最古年が未登録なら現行どおり1975年を用いる。

| 入力・経路 | 許可範囲 | 拒否と代表例 |
| --- | --- | --- |
| 地点 | 登録済みの正整数ID | 整数でない値・0・負数は422、未登録の正整数は404 |
| 都道府県フィルター | 地点マスタに存在する都道府県番号、省略時は全地点 | 不正形式は422、存在しない番号は404 |
| キャッシュ参照の終了年 | 地点の最古年〜日本時間の今年、省略時は今年 | 最古年−1、今年＋1、0、10000は422 |
| キャッシュ参照の範囲 | `max(最古年, 終了年−49)`〜終了年、最大50年 | 任意の開始年による範囲拡張は提供しない |
| 月別取得の年 | 地点の最古年〜今年 | 最古年−1、今年＋1は422 |
| 月別取得の月 | 1〜12、かつ今月以前 | 0・13・未来月は422（空配列からの変更） |

数値形式の受理はFastAPIの整数パラメーターとし、非整数文字列と小数は422。地点未登録の判定は年月の意味検査より先とする。
既知の地点の最古年1月、今年の今月、終了年が最古年と等しい場合を正常系として検証する。
登録年しかないため、最古年の観測開始前の月は空データを許す。未知のqueryは現行どおり無視し、範囲を広げない。
不正入力では気象庁へ接続せず、気温・取得ログを書き込まない。404・422は自動再試行しない。

## 気象庁への取得方針（#198）

キャッシュに有効データがあれば上流取得枠を消費しない。空データの成功も取得済みとして扱い、失敗は成功ログにしない。
未取得・要更新時は共有ストアの条件付き更新で全地点共通の取得leaseを確保し、実行環境をまたいで同時取得を1件に抑える。
lease取得後に鮮度を再確認し、他実行が完了済みならキャッシュを返す。
占有中の要求は待機キューに積まず503と`Retry-After: 5`を返す。同じ地点・年月への要求もこの扱いとし、失敗した要求は後から再試行できる。
上流試行開始の間隔を全体で最低2秒にし、リトライも枠を取り直す。最大3試行、2秒・4秒のバックオフ、失敗終了後の不要なsleepは行わない。

leaseは30秒固定とし、所有tokenによって確認・解放し、期限切れ時の引き継ぎを条件付き更新で行う。25秒の取得予算内で終了させるため延長は不要とする。DynamoDB TTL削除時刻を排他条件に使わない。
上流I/Oは1試行8秒の総時間制限、全試行・バックオフを含む取得予算は25秒。期限超過は503にする。
leaseは30秒とし、所有権を失った実行は次の上流試行・書き込みを行わない。停止中のプロセスが期限後に動き出す場合の一時的な重複まで厳密に防ぐ保証はしない。
HTTP APIの応答待ち時間内で終了するかは#198の統合検証で確認し、満たせなければ適用前に仕様を見直す。
ブラウザを閉じた後のサーバー処理中止は保証しない。

## 容量設定と根拠（#199で実装）

初期の設計対象は、通常の閲覧者2人が各1本の月別取得を行い、応答後2秒以上待つ利用とする。実測需要の主張ではなく、初期の検証条件である。

| 対象 | 初期提案値 | 根拠と限界 |
| --- | --- | --- |
| HTTP API stage | rate 5 requests/s、burst 10 | 2人分の初回一覧・キャッシュ参照の短い集中に余裕を持たせる |
| 月別取得の明示route | rate 1 request/s、burst 2 | 通常2人の最大約1 request/sを基準にする。全体上流枠の競合は503で通知する |
| Lambda reserved concurrency | 5 | 上流待ち1件と軽い参照用の余地を設ける。ただし要求種別ごとの枠予約にはならない |

同じLambdaなので、遅い参照や悪用で正常閲覧を妨げる可能性は残る。利用者別公平性は保証しない。
#199では`GET /api/temperature/{station_id}/fetch-month`の明示routeを追加して同じintegrationへ接続し、stage既定値とroute値の両方を確認する。HTTP APIのCORSにも`expose_headers = ["Retry-After"]`を設定し、統合応答の待ち時間をブラウザへ公開する。
CORSはブラウザの読み取り許可であり、認証にも流量制限にもならない。
API Gatewayの制限はbest effortで、厳密な天井ではない。Lambda concurrencyは同時実行を抑えるが、継続時間・呼出回数・DynamoDB・転送等の費用上限を保証しない。

## エラーと再試行UI（#198・#199）

アプリケーションの負荷拒否は503、Gatewayの流量拒否は429。Lambda呼び出し拒否・Gateway timeoutはGateway由来の5xxになりうるため、すべてを429に正規化する前提を置かない。
アプリケーションは`detail`で固定の安全な説明を返し、例外・AWS識別子を返さない。GatewayのJSON形式や`Retry-After`の存在は保証しない。
ブラウザは429・503・Gateway由来5xx・通信失敗で取得ループを停止し、表示済みデータを維持する。残りの月を失敗のまま連続送信しない。
「混雑または一時的な問題で取得できません。しばらく待って再試行してください」と再試行操作を示す。
再試行は手動のみ。整数秒の`Retry-After`が1〜60ならそれを使い、それ以外は5秒待ってボタンを有効化する。CORSで当該ヘッダーを公開する。
再試行では同じ地点・期間をキャッシュから再評価し、取得済み月を取り直さない。地点変更は待機中も可能で、前地点の遅い応答は表示へ反映しない。

## #198の保存契約と運用上の境界

共有leaseは既存fetch-logテーブルの`station_id=0`、`year_month=__upstream_lease__`に保存する。地点IDは正整数なので気象データの取得記録と衝突しない。TTL削除・新テーブル・追加IAM権限は使わない。全参加者を#198の版へ揃えた後にのみ共有抑制が有効になる。旧版との混在中は保証しない。取得記録の再確認は強い整合性で行う。

25秒はlease取得後の上流取得・バックオフの予算。DynamoDBの同期I/O、パース、保存、解放と応答の時間は別に加算されるため、API Gatewayの待ち時間内の成功を保証しない。Gateway timeout後も処理が残る場合は既存キャッシュを次の手動再試行で再評価する。後続の非本番環境で実際の応答時間を確認してから本番へ適用する。

上流枠の解放時にも完了時点から2秒の待ち時間を保存し、SDK応答の遅延が次の所有者との間隔を縮めないようにする。
条件付き更新と非同期の時間制限の根拠は[DynamoDBの条件式](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html)と[Python 3.14のtimeout](https://docs.python.org/3.14/library/asyncio-task.html#timeouts)を参照する。

## 時刻依存の境界（#198）

Domainの`Clock` PortがUTC現在時刻と単調増加の経過時間を提供し、Infrastructureの`SystemClock`だけが`datetime.now()`と`time.monotonic()`を呼ぶ。UseCase、共有lease、取得ログ保存にはDIで同じ時計を注入する。日本時間の観測年月への変換は純粋な業務ルールとして保持する。固定時計によって年境界・lease失効・壁時計補正と取得予算の独立性を検証する。日時の値型と日付計算はPython標準の`datetime`を継続使用する。

## 公開APIのCORS契約

公開業務APIのmethodはGETのみで、fetch-monthも既存のGET契約を維持します。CORSはブラウザからの応答読み取りを許可する設定であり、認証や非ブラウザのアクセス制御ではありません。
本番の許可originは既存のfrontend HTTPS origin 1件、資格情報の許可はfalseです。OPTIONSはpreflightの処理であり、業務methodには含めません。
許可request headerはAccept / Accept-Language / Content-Language / Content-Typeで、Authorizationや任意headerは許可しません。
最初の3件はブラウザとStarletteのsafelisted headerに相当し、Gatewayにも明示して集合を揃えます。frontendのGETはContent-Type: application/jsonを使うため、そのpreflightを許可します。
Retry-Afterの公開とGateway既存のmax_age=86400を維持し、アプリも同じ値へ揃えます。開発環境のorigin設定は従来どおり環境設定から取得します。

HTTP APIはCORS設定時にbackendのCORS headerを上書きするため、アプリ単体の成功だけで本番Gatewayの一致を保証しません。
[適用・検証手順](../infrastructure/docs/api-cors.md)に従い、設定照合と本番通常利用を別途確認します。
