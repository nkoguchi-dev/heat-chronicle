# 仕様書レビューガイド

この文書は、Markdown仕様書、Gherkin、技術資料を作成または変更するPull Requestの自己レビュー観点を定義する。[全体共通レビューガイド](./REVIEW_GUIDE.md)と併用する。

自己レビューでは該当する項目を確認し、対象外の項目は理由を記録する。自己レビューは人による仕様確認を置き換えない。

## 1. 目的と読者

- [ ] 文書の目的と、利用者、プロダクトの判断者、エンジニアなどの主な読者が明確か
- [ ] 利用者から見える状態、操作、振る舞い、提供範囲、制約を認識合わせできる言葉で記載しているか
- [ ] 対象外、既知の制約、後続Issueを決定済みの仕様と区別しているか

## 2. 文書の責務

### Markdown仕様書

- [ ] APIフィールド、HTTPステータス、クエリパラメータのキー名、関数、型、コンポーネント、状態管理などの実装依存情報が混在していないか
- [ ] 実装依存情報を記載する場合、それ自体が利用者との合意対象である理由があるか
- [ ] エラーを技術的原因だけで表さず、利用者が理解できる状態、案内、次の操作として定義しているか

### Gherkin

- [ ] Markdown仕様書の振る舞いと対応し、利用者から観測できる前提、操作、結果を表しているか
- [ ] API呼び出し、レスポンス、内部状態、関数、コンポーネント名を受け入れ条件にしていないか
- [ ] 正常系だけでなく、主要な境界、ローディング、エラー、再試行、アクセシビリティを扱っているか
- [ ] 各ScenarioとScenario Outlineに`@smoke`または`@regression`が付いているか
- [ ] 同じ振る舞いをタグごとの別シナリオやBrowser Smokeへ重複させていないか
- [ ] 関連テストの追加・更新、または更新不要とした判断を自己レビューへ記録しているか

### 技術資料

- [ ] 外部API、ライブラリ、内部構造に依存する事実と実装判断を利用者向け仕様から分離しているか
- [ ] 技術的な事象と仕様書で定義した利用者向け状態の関係を確認できるか
- [ ] 確認日、対象バージョン、一次情報へのリンクなど、再確認に必要な情報があるか

## 3. 正本と参照関係

- [ ] Markdown仕様書を利用者向け仕様の正本、Gherkinを観測可能な具体例として扱っているか
- [ ] Markdown仕様書とGherkinが矛盾していないか
- [ ] 追加・移動・削除した文書に合わせて索引、README、関連資料のリンクを更新しているか
- [ ] 技術資料が利用者向け仕様の正本であるかのように記載されていないか

## 4. 変更の一貫性

- [ ] 関連するMarkdown仕様書、Gherkin、技術資料、テスト、README、既知の制約への影響を確認しているか
- [ ] 利用者向け仕様の変更をMarkdown仕様書とGherkinへ同じPull Requestで反映しているか
- [ ] 外部仕様を変えない実装変更で、仕様書を不要に変更していないか
- [ ] 未実装の要件や後続Issueを、現在の実装済み機能と区別しているか

## 5. PRコメントへの記録

自己レビューコメントには、少なくとも次を記載する。

- 変更した仕様と、判断が必要だった境界
- Markdown仕様書、Gherkin、技術資料の更新内容または更新不要とした理由
- 実装依存情報が仕様へ混在していないことの確認結果
- 仕様とGherkinの対応、および関連テストの更新要否
- 人によるレビューで重点的に確認してほしい点
